# Configuration

Orrery reads one YAML file. Topology, environments, naming rules, freshness targets, and visual
settings all live there, so a new deployment never needs a source edit. The examples in
`config/examples/` are a good starting point: `demo.yaml` (all mock, the quick-start default),
`three-env.yaml` (mock dev with Databricks stg and prod), `single-workspace.yaml`, and
`multi-metastore.yaml`.

## File location and the private overlay

The server loads the file named by `ORRERY_CONFIG`. A relative path resolves against the working
directory. When the variable is unset, the server logs a warning and uses the demo config
(`config/examples/demo.yaml` from source, or `config/demo.yaml` inside the packaged app).

```sh
ORRERY_CONFIG=config/private/orrery.config.yaml node apps/server/dist/main.js
```

Everything in `config/private/` except its README is git-ignored. A fork keeps its real config
there, so organization details never reach the public repository (see `docs/forking.md`).

Add this line at the top of a config file for validation and completion in editors that use the
YAML language server:

```yaml
# yaml-language-server: $schema=../../packages/core/schema/orrery.config.schema.json
```

The schema is generated from the zod types in `packages/core/src/config/` and committed, and CI
fails when the two differ. It covers the shape of the file. Checks across keys (unknown topology,
duplicate ids, promotion order) run only in the server's validator (decision 16).

Other environment variables that affect configuration:

| Variable                                   | Effect                                                                  |
| ------------------------------------------ | ----------------------------------------------------------------------- |
| `ORRERY_CONFIG`                            | Path of the config file.                                                |
| `HOST`, `PORT`                             | Listen address. Defaults to `127.0.0.1:8787`.                           |
| `DATABRICKS_APP_PORT`                      | Set by Databricks Apps. Used as the port and implies host `0.0.0.0`.    |
| `MOCK_SEED`, `MOCK_SPEED`                  | Mock adapter seed override and live-time multiplier (decision 28).      |
| `ORRERY_TRUST_FORWARDED_TOKEN`             | Set to `1` to trust the forwarded viewer token outside Databricks Apps. |
| `ORRERY_WEB_DIR`                           | Directory of the built web app that the server serves.                  |
| Any name used in a `${env:NAME}` reference | Resolved by the adapter at runtime.                                     |

## Secrets: `${env:NAME}`

Secret fields (`connection.clientId`, `connection.clientSecret`, `connection.token`) accept only a
reference of the form `${env:NAME}`, where `NAME` matches `[A-Z_][A-Z0-9_]*`. A literal value fails
validation, so a secret cannot be committed by accident. `connection.host`, `connection.warehouseId`,
and the metastore `host` and `warehouseId` are not secrets, so they may be literals or references.

The validator checks only the form. The adapter reads the variable from the process environment
when it needs it. A missing or empty variable counts as "not set", and error messages and logs
never contain the value.

Quote a reference inside a YAML flow mapping (`{ ... }`), because an unquoted `${` breaks the
parse (decision 1):

```yaml
metastores:
  - { id: primary, host: '${env:ORRERY_PROD_HOST}', warehouseId: '${env:ORRERY_PROD_WAREHOUSE}' }
  # block style needs no quotes
  - id: secondary
    host: ${env:ORRERY_PROD2_HOST}
```

## Matchers

Nothing that identifies a real platform object is a hard-coded name. Spokes, source groups, and
use cases carry a `match` block with at least one of these keys (listed at the end of the
reference):

- `catalog`, `schema`: globs. `*` matches any run of characters, `?` one character, and matching
  is case-insensitive.
- `tag`, `pipelineTag`, `jobTag`, `dashboardTag`: key and value maps of tags.

When a matcher has several keys, all of them must match. The Databricks adapter evaluates schema
clauses (`catalog`, `schema`, `tag`) against schemas, with the environment tag stripped from the
catalog name, and `pipelineTag` and `jobTag` against pipelines and jobs (decision 54).

```yaml
- id: sales
  match: { schema: '*_sales_*' } # a schema glob
- id: finance
  match: { tag: { domain: finance } } # a Unity Catalog tag
- id: region-a
  match: { pipelineTag: { source_region: a } } # pipelines carrying a tag
```

## Topologies: `extends`, `exclude`, `overrides`

`topologies` is a map of named topologies. An environment picks one by name, and a topology can
inherit from another:

```yaml
topologies:
  base:
    hub: { id: core, name: Core platform }
    spokes:
      - id: ingest
        name: Regional ingest
        role: ingest
        match: { tag: { domain: ingest } }
        freshness: { cadenceMinutes: 15, targetMinutes: 21 }
      - id: finance
        name: Finance
        role: domain
        match: { tag: { domain: finance } }
        freshness: { cadenceMinutes: 1440, targetMinutes: 1560 }
  dev:
    extends: base
    exclude: [finance] # dev has no finance spoke
    spokes:
      - id: ingest # merges with the inherited spoke of the same id
        freshness: { cadenceMinutes: 60, targetMinutes: 90 }
```

The rules (decision 9):

- `spokes`, `sourceGroups`, and `useCases` merge with the base **by `id`**. A matching id merges
  field by field, and a new id is appended.
- The merge is one level deep. A nested object such as `freshness` or `match` is replaced as a
  whole, not merged key by key. `hub` merges field by field. `medallion` and `shipyard` are replaced.
- `exclude` lists ids to drop from the inherited lists.
- An entry that overrides a base entry needs only its `id` plus the fields it changes. A topology
  is checked for completeness after resolution, and errors name the environment and the
  topology.
- An environment can apply the same shape under `overrides`, on top of its topology, without
  creating a separate topology.
- A cycle in `extends` is an error.

## Environments and scope

`environments` is a list, not a fixed set. Each has an `id`, a `tier`, a `topology`, and an
`adapter`. Faces and the environment switcher follow `promotion.order`; environments it omits
follow in config order.

Scope applies to the Databricks adapter (decision 54, `docs/databricks.md`). An environment owns
the catalogs that match its `scope.catalogs` globs, or that carry every tag in `scope.tag`:

- The environment tag may sit at the start or the end of the name, so list both forms:
  `['dev_*', '*_dev']`. Matching is case-insensitive.
- Spoke matchers then run against the catalog name with the environment tag stripped, so
  `dev_sales` and `sales_dev` both resolve to the Sales spoke.
- A catalog that matches two related environments fails the health check and names both. This is a
  runtime check, because it needs the live catalog list (decision 14).
- Catalogs that match no environment are ignored and listed in the environment's health as
  `unmatchedCatalogs`.
- An environment with no `scope` owns every catalog that no peer claims. Platform catalogs
  (`system`, `samples`, `hive_metastore`, and names starting with `__`) are never owned.

## Validation errors

Every object in the schema rejects unknown keys. The error carries the path, a suggestion when a
close key exists, and the allowed keys. The server prints the message and exits with code 1 when
the file is invalid, and no environment starts. These two errors come from a real invalid file.
Checks across keys run after the shape is valid, so a file shows them in two rounds.

Shape errors (a misspelled key, a missing key, a literal secret):

```text
config/private/orrery.config.yaml: 3 config problems
  - topologies.base.spokes[0].freshness.targetMinutes: Invalid input: expected number, received undefined
  - topologies.base.spokes[0].freshness: Unknown key "targetMins". Did you mean "targetMinutes"? Allowed keys: cadenceMinutes, targetMinutes, offsetMinutes.
  - environments[0].connection.clientSecret: Secret fields accept only an environment reference such as ${env:ORRERY_TOKEN}; never put a literal secret in config.
```

Reference errors (unknown topology, adapter, or environment):

```text
config/private/orrery.config.yaml: 3 config problems
  - environments[0].topology: Unknown topology "bse". Did you mean "base"? Defined topologies: base.
  - environments[0].adapter: Unknown adapter "databrics". Did you mean "databricks"? Register fork adapters under "adapters".
  - promotion.order[0]: Unknown environment "prd". Did you mean "prod"?
```

YAML syntax errors, including duplicate keys, are reported with the path `(yaml)`.

resolved. The `environments[].overrides` block has the same keys as a topology without
`extends`, so it is listed as one row.
